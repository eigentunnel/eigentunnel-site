Developers and test labs

A narrow public path for real technical review.

Core Public is designed to answer a specific question: can a reviewer build the lab kernel, inspect the cryptographic boundary, and run synthetic tests without receiving the commercial product?

What labs can test

The public surface is intentionally small.

Crypto and identity

Hybrid key establishment, ML-DSA identity behavior, AEAD packet protection, and negative tests around invalid material.

Transport primitives

QUIC/session/framing primitives, packet routing, and local pipeline behavior under synthetic conditions.

Config boundary

Sanitized TOML parsing and validation that makes the public profile explicit and keeps private modes out of the public branch.

What labs do not get

The store stays private.

No Cloud workflow

No enrollment service, tenant workflow, approvals, evidence engine, reports, CBOM generator, OSCAL package, or integrations.

No product packaging

No production installer, daemon packaging, managed gateway/relay productization, field scripts, customer topology, or performance claims.

No private profiles

Commercial profiles, hardened feature paths, and proprietary functions require private access under written terms.

Recommended lab flow

Keep the review repeatable.

  1. Build Core Public from a clean checkout.
  2. Run the documented workspace and crate-level test recipes.
  3. Review fixture provenance and confirm all inputs are synthetic.
  4. Record questions against the public boundary before requesting private access.
  5. Move to private Core or Cloud only under NDA, pilot scope, or commercial agreement.
Core Public is not production authorization. It is a controlled review surface.
